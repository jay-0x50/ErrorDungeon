# Tech/Deploy 추가 — Unity 서버 옵션 검토 (채점 조건 대조)

## 0. 결론 요약

- 유니티는 **Ubuntu 24.04에서 헤드리스(Dedicated Server) 빌드로 실행 가능** — 문제 없음.
- 다만 리눅스 수행평가 채점표는 "브라우저로 도메인 접속 시 서버가 매번 새로 만들어주는 HTML"을 요구하는데, 유니티 기본 네트워킹(Netcode/Mirror 등)은 게임 전용 TCP/UDP 소켓이라 **Nginx가 그대로 프록시할 수 없음**.
- 그대로 "유니티 서버만" 채점 대상으로 제출하면 **조건 2·3번에서 걸릴 위험**이 있음. 아래 두 가지 방식 중 하나로 보완 필요.

---

## 1. 유니티 리눅스 서버가 기술적으로 가능한 이유

- Unity Build Settings에서 **Platform: Dedicated Server, Target Platform: Linux**를 선택하면 GUI 없는 헤드리스 실행파일이 만들어짐(공식 지원, 2020 LTS 이후 전 버전).
- 빌드는 개발 PC(Windows 등)에서 하고, **VM에는 빌드된 실행파일만 복사**하면 됨 — VM에 Unity Editor 설치나 라이선스 활성화가 필요 없음.
- 실행 시 `./ServerBuild.x86_64 -batchmode -nographics` 형태로 콘솔에서 그냥 돌릴 수 있어서, systemd 유닛의 `ExecStart`에 그대로 넣을 수 있음.
- 전용 계정 소유/권한, ufw 포트 제한 등은 다른 리눅스 프로세스와 동일하게 적용 가능.

## 2. 채점표 8개 조건 대조

| # | 조건 | 유니티 서버만 썼을 때 | 비고/대응 |
| --- | --- | --- | --- |
| 1 | 우분투 24.04에서만 | **충족** | Dedicated Server Linux 빌드가 Ubuntu 24.04 x64에서 정상 구동 |
| 2 | 리버스 프록시 필수(브라우저는 Nginx 80번에만) | **위험** | 유니티 기본 통신은 HTTP가 아니라 게임 소켓이라 Nginx가 프록시할 대상이 없음 → 3장 방식 중 하나 필요 |
| 3 | 정적 페이지 금지, 서버가 매번 동적으로 생성 | **구현 필요** | 유니티 코드가 요청마다 HTML을 만들어 응답하게 직접 짜야 충족됨(3장 A안) |

| 8 | 1차 계획서와 값 일치 | **문서 수정 필요** | "사용 기술" 항목을 Flask 등에서 Unity(C#)로 바꾸면 4장에 변경 사유 명시 |

## 3. 구현 방식 두 가지

### A안 — 유니티 안에 HTTP 응답 코드 직접 넣기

- 유니티 서버 프로젝트에 `System.Net.HttpListener`(또는 경량 HTTP 라이브러리)를 붙여서 `127.0.0.1:포트`로 GET 요청을 받고, 동적 HTML(예: 현재 접속자 수, 서버 시각, 처치된 보스 수, 리더보드 Top 5)을 문자열로 조립해 응답.
- HttpListener는 별도 스레드에서 요청을 처리하므로, 게임 메인 스레드의 상태값을 읽을 때는 락(lock)이나 스레드 안전 큐를 통해 접근해야 함.
- **장점**: "내 게임 서버가 직접 화면을 만든다"는 걸 보여줄 수 있어 프로젝트 완성도/차별성이 높음.
- **단점**: C#으로 raw HTTP 서버를 직접 짜야 해서 공수가 큼. 수업에서 배운 Flask 패턴과 다르므로, 시연 때 "이게 왜 서버인지" 본인이 설명하지 못하면 최대 15점 감점 조건에 걸릴 수 있음 → 반드시 본인이 코드를 이해하고 설명할 수 있어야 함.

### B안 — 역할 분리(권장)

- 리눅스 배포 수행평가 제출용 웹앱은 기존 계획대로 **FastAPI/Flask/Node**로 만든다(Tech Deploy 문서 3.1 리더보드 API 그대로 활용).
- 그 웹페이지가 보여주는 값(리더보드, 접속자 수, 최근 처치 보스 등)은 **유니티 서버가 기록한 세이브/랭킹 DB**에서 읽어와 표시한다.
- 즉 "유니티는 게임 로직을 돌리는 별도 프로세스, 경량 웹서버는 그 결과를 브라우저에 보여주는 창구"로 역할을 나눈다.
- **장점**: 채점 조건 8개를 안전하게 충족하면서도, 유니티 리눅스 서버 운용 경험이 실제 프로젝트에 그대로 들어감. 수업에서 배운 웹 프레임워크 구조도 그대로 활용 가능.
- **단점**: 유니티 서버와 웹앱 프로세스가 분리되므로, 둘 사이에 같은 DB(SQLite/PostgreSQL) 또는 파일을 공유하는 연동 로직이 한 단계 더 필요.

## 4. 권장 결론

- **채점용 제출물은 B안**으로 간다. 안정성이 훨씬 높고, 기존 Tech Deploy 문서 구조(3.1/3.2)와 그대로 맞아떨어짐.
- 유니티 리눅스 서버 자체는 "게임 로직/랭킹 기록 담당 프로세스"로 프로젝트 구조에 정식으로 추가한다(아래 5장 반영).
- 시간이 남고 더 하고 싶다면 A안(유니티가 직접 HTML 응답)을 추가 도전 과제로 남겨둔다 — 단, 계획서 8번 조건(계획서와 일치) 때문에 방식을 바꿀 경우 1차 계획서 대비 변경 사유를 꼭 적어야 함.
